# 联机协议与验证（v2）

StarRailCard 与相邻的 `hearthStoneKill2` 使用同一个公共 MQTT 服务。浏览器直接通过 WSS 连接，无需自建服务器。

## 服务器与房间

- 默认：`wss://broker.emqx.io:8084/mqtt`；备用：`wss://broker-cn.emqx.io:8084/mqtt`、`wss://broker.hivemq.com:8884/mqtt`。
- 新主题前缀为 `starrailcard/v2`，与旧 v1 和 hearthStoneKill2 的 `sgskill3` 完全隔离。双方必须使用新版客户端。
- 房间号为六位数字。邀请链接携带房间号和服务器；备用服务器不自动接管旧服务器的对局。
- 经典 1v1 和双人共斗仍为两名真人；多人派对 `treasure` / `raid` / `duos` / `overlord` 可开 4～8 个席位（搭档模式只接受偶数）。空位可由游戏层补入 AI，所有 AI 指令由房主驱动。多人仅支持好友房；原模式公开匹配流程保留。
- 主题：`rooms/<code>/room` 为房间信息，`state` 为完整快照或增量更新，`intent` 为操作，`response/<playerId>` 为确认，`heartbeat` 为心跳。公共匹配使用 `match/<mode>/<code>`。
- 房间信息、完整快照、候选广告使用 retained；增量、意图、确认、心跳不保留。首次加入后主动请求最新快照，不能把 retained 的初始快照当作最新对局。

## 本地交互与权威节点

大厅中更换角色、曜彩骰或镀闪时先更新本地预览，再异步提交配置，其他玩家无需等对方准备即可看到。换卡上传不锁住选择器。配置与准备操作带递增控制时间，连续换卡后立即准备时，延迟到达的旧配置不能覆盖最新角色或取消准备。

点击、取消和滑选骰子以及攻防预览只改变界面草稿，不经过 `sendCommand()`，不保存联机检查点，也不等待服务器。确认时发送一个 `confirm { playerId, diceIds }`，房主在一次引擎操作中验证全部骰子并确认。重投发送目标骰子 ID；曜彩骰、交换、战术操作仍由房主裁定。

房主自己的指令直接进入本地权威队列，和客人的意图串行执行，不绕 MQTT 发回自己。合法操作记录结果并持久化后，本地主人立即得到结果；向另一端广播与确认在独立发送队列完成。随机数和伤害只由房主推进。

联机 1v1 每局由房主使用浏览器生成的新随机种子，以等概率抽取双方先后手，再将完整初始局面同步给客人。房主身份与先手无关；回房重开重新抽取，断线恢复沿用已保存的攻防顺序。共斗仍由队伍先攻。

`OnlineSession<S,C>` 接受 `reduce(state,command,context)`、`commandScope` 和 `stateCodec`。经典与共斗使用 `gameCommandScope` / `gameStateCodec`，多人派对使用 `src/net/partySync.ts` 中的独立适配器。上下文包含席位、玩家 ID、当前版本及对局 `matchId`。集成层继续验证操作者所有权，只允许房主驱动 AI。

每个房间有随机 `epoch`，每局另有随机 `matchId`。每名玩家有递增 sequence，每条意图有唯一 ID。scope 覆盖 matchId、回合、阶段、攻防方、首领阶段和操作者骰池及可操作标志；战术按相关库存补充 scope。队友的独立确认不会改变自己的 scope，所以两人同时确认可以依次在最新版本上生效。自己的骰池或阶段变化则拒绝旧操作。共斗交换的目标骰所有权仍由引擎逐次验证，争抢同一骰只有一次成功。

## 传输、去重与恢复

- 开局或请求同步时发送完整快照。常规状态包含 baseVersion、新 version、matchId 和发生变化的动态字段；不可变 catalog 不重发。经典与共斗按新增事件发送日志，多人派对发送变更后的日志窗口（最多 160 条）。
- 确认只包含 ID、sequence、是否成功、错误说明、已提交版本及 sequence 高水位，没有第二份 game。跨主题收到确认早于状态时先等待状态，不提前解锁或重复结算。
- 收到增量时要求 baseVersion 与本地相等；缺版、无法解码或心跳发现落后就请求完整快照。确认后丢失状态也在重试窗口补全。
- 每 1.5 秒重发同一 ID/sequence。轻量 receipt 窗口随人数扩展（至少 24 条），并持久化 sequence 高水位；重复指令只重发确认，不重新执行规则。未来 sequence 等待前序，已超出 receipt 窗口的旧 sequence 仍被高水位拒绝。
- 每 5 秒发心跳和轻量房间元数据，不广播整局。16 秒没收到对方心跳暂停，最多保留两分钟，超时记中断而不伪造胜负。
- `OnlineSnapshot.matchId` 标识局次；`recoveryRevision` 只在实际补全/重连时变化，让界面放弃旧草稿、跳过历史演出。同 matchId/同 version 的重复快照不会重置选择或中断当前动画。房主自己的传输重连同样更新恢复标记。
- v2 检查点保留随机数、版本、序列和 receipts。房主刷新等待队友恢复后继续；客人重新连接主动同步权威状态。旧 v1 联机检查点明确提示双方更新并重新建房，养成存档保留。
- 离开房间、加入新房、创建新房时清空该 epoch 的 sequence、receipt 与准备时间等会话计数；复用同一浏览器客户端换房时，新房首条指令始终从 sequence 1 开始。排队旧房指令也验证 epoch/matchId，不能在新房误执行。
- `returnToLobby()` 保留席位与配置、清空准备状态，下局生成新 matchId。`destroy()` 用于刷新保留恢复机会；`leave()` 主动离开并清空本地检查点。

JSON 单包上限保持 256 KiB，MQTT QoS 1 加应用确认。30 条真实引擎命令的尺寸回归中，经典最大增量为 7,087 字节，共斗为 9,475 字节，确认最大 214 字节；开局完整快照分别约 44.5 KB / 46.1 KB。公共 broker 提供休闲同步，不提供账户认证、私密房间或服务保证；已知主题的人可以订阅或伪造数据。房号用于定位，不是密码。协议不传密码、邮件等个人信息。

## 验证方法

```powershell
npx vitest run tests/net-session.test.ts tests/net-game.test.ts tests/net-live.test.ts
```

当前 30 项本地网络测试通过，默认跳过 4 项公网测试。FakeBroker 验证丢包、重排、重复、同版本快照、sequence 间隙、原子确认、并发交换、重开隔离、断线和刷新恢复。300 ms 与 1000 ms 人工时延下，真实共斗引擎同时确认成功，客人仅一条 confirm 意图、房主零条 self-intent；本地选骰零指令由界面草稿测试覆盖。

游戏状态回归检查完整快照低于 256 KiB，常规增量没有 catalog/历史日志，确认没有 game，并验证 JSON 序列化和 160 条日志窗口。

真实公网验证：

```powershell
$env:SRC_MQTT_LIVE='1'
npx vitest run tests/net-live.test.ts --reporter=verbose
Remove-Item Env:SRC_MQTT_LIVE
```

两个独立 MQTT 客户端通过默认 EMQX 同步真实游戏命令，逐轮比较双方状态，客人在已有战斗记录后刷新一次，再继续完成终局。首领 AI 指令只由房主提交。测试后清理临时房间和 retained 消息。这是协议与引擎的公网集成验证，不等同于两名玩家在浏览器中手工验收 UI。

### 跨房间复用补充（同日）

真实双标签页发现同一客人客户端从旧房加入新房时沿用旧 sequence，导致新房主等待 sequence 1、购买长时间未确认。现于离房／新加入／建房清空 epoch 内计数，并阻止旧房排队指令流入新房。

新增两项本地回归覆盖同实例跨房首序号及「经典投降→回大厅→关闭→新共斗→购买 2 点战术」。另外单独运行真实 EMQX 跨房 smoke，19.69 秒通过：同两个 MQTT 客户端连续进入 duel 与 coop 两个新 epoch，不刷新客人实例，每房首条指令均从 sequence 1 开始并得到一致状态。

本轮公网证据合计 4 项：上文 3 项完整验证，以及这里单独执行的 1 项跨房验证；没有把它们写成一次完整套件的耗时。
